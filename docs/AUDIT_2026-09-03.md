# CSCA Prep full product audit — 2026-09-03

## Executive decision

The application is ready to use as an **honestly labelled local practice demo**. It is not
yet ready to be the learner's only source of CSCA preparation or to claim production-grade
scores, synchronization, or mock exams.

| Area | Rating | Decision |
| --- | ---: | --- |
| Engineering and architecture | 8.5/10 | Strong foundation |
| UX and responsive design | 8/10 | Good on desktop, iPhone and iPad |
| Performance and accessibility | 9/10 | Strong measured results |
| PWA and offline demo | 8/10 | Works; real Safari install remains unproved |
| Security design | 8/10 | Strong code controls; demo host is weaker |
| Learning system | 7/10 | Good mechanics and honest zero states |
| Verified CSCA content | 2/10 | The main blocker |
| Production readiness | 4/10 | Firebase/Vercel and real sync are not deployed |

**Overall:** start using the demo now to test the learning flow and record feedback, but do
not treat its readiness score or generated demo questions as a validated prediction of the
real exam. The next major investment must be reviewed content, not more visual polish.

## What is already strong

### Learning and UX

- Five-step onboarding collects the real exam date, starting Mathematics/Physics levels,
  explanation language and daily time budget.
- A missed study day is handled explicitly: shift, compress, or keep the calendar. The app
  never silently changes the learner's plan.
- Onboarding levels act only as a fading prior; measured answers replace them.
- Practice keeps the sequence of understanding, answer, confidence and feedback.
- Vocabulary and formula reviews persist mastery, interval, due date, lapses and outcome.
- Progress views distinguish measured data from empty states and internal readiness metrics.
- A 48-question, 60-minute demo mock matches the current published Mathematics/Physics
  format, but is correctly labelled as local and unofficial.
- Bilingual explanation infrastructure exists, with an honest fallback when a translation is
  missing.

### PWA and persistence

- Valid web manifest, install icons, standalone display, safe-area handling and update prompt.
- Service worker avoids caching Google/Firebase API responses and sensitive answer material.
- Local-first persistence, an outbox, sync cursor, conflict records and owner isolation exist.
- Demo state survives reload. Cloud cross-device restoration is implemented but not proved
  against a production Firebase project.

### Security and privacy

- No runtime `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `new Function`, unsafe redirect,
  unsafe `postMessage`, or dynamically injected third-party script was found.
- Authentication and authorization are server checked for trusted operations; App Check,
  schema validation, rate limits, audit logs and server-owned mock timing/grading exist.
- Private question import separates learner-readable prompts from server-only solutions.
- The AI tutor seam is disabled by default, with quotas, a kill switch, exam-mode refusal,
  prompt-injection fencing and a verified non-AI fallback.
- Export, reset and reauthentication-protected account deletion flows exist.
- No known production dependency vulnerability remains after the remediation in this audit.

## Critical gaps

### P0 — blocks a trustworthy production learning product

1. **No production environment.** GitHub Pages is a local demo. Firebase/Vercel has not been
   deployed and Google sign-in, App Check, server callables and two-device sync are not
   proven on a real domain.
2. **Zero human-verified blueprint coverage.** There are 105 draft blueprint cells (46
   Mathematics, 59 Physics), 17 original public practice questions and no human-approved
   item. Coverage is therefore 0/105 by design.
3. **No confidential production mock bank.** The 17 seed keys are in public Git history and
   cannot count for mock coverage. A private bank must be authored, independently reviewed
   and imported without entering the repository.
4. **Blueprint provenance still needs a qualified human review.** The current seed is derived
   from the repository curriculum and explicitly does not claim to be the official syllabus.
   It must be checked cell by cell against the current official CSCA materials before coverage
   targets become authoritative. In particular, physical optics (interference/diffraction)
   and kinetic theory should be explicitly verified rather than inferred from broad topics.
5. **Legal drafts are not publishable policy.** Privacy/terms files are labelled drafts and
   contain deployment-specific decisions/placeholders that require the operator and, where
   appropriate, legal review.

### P1 — required before relying on progress across devices

1. Test sign-in, onboarding restoration, sync, conflicts, reset and deletion on two real
   accounts and two real devices.
2. Run Firestore/Auth/Functions/Storage emulator abuse tests, not only source-contract tests.
3. Test iPhone Safari and iPad Safari: install, update prompt, offline reopen, keyboard,
   rotation, safe areas and background/foreground timer behavior.
4. Add production monitoring for callable errors, sync failures, import conflicts, account
   deletion failures and mock submission latency, without logging question keys or learner
   free text unnecessarily.
5. Calibrate readiness against real reviewed item difficulty and later against anonymized exam
   outcomes; until then it must stay labelled an internal planning metric.

### P2 — highest-value product improvements after P0/P1

1. Grow reviewed content in narrow vertical slices: lesson -> guided practice -> spaced
   review -> timed mixed set -> private mock. Finish a cell completely before spreading thinly
   across all 105 cells.
2. Add an official-outline comparison screen for administrators with source date, reviewer,
   last checked date and unresolved differences. Do not copy restricted official material.
3. Add concise concept resources and short original videos only where a visual explanation
   materially improves understanding; attach each resource to a blueprint cell and verify it.
4. Add learner-visible coverage confidence: what has been studied, what is reviewed, what is
   only demo content and what remains unmeasured.
5. Add score-confidence bands only after enough validated data exists. A precise-looking
   prediction without calibration would be worse than the current honest readiness label.
6. Reduce initial JavaScript further by separating Firebase authenticated services and heavy
   chart/math packages from the first anonymous/onboarding load.

## Security findings

### SEC-01 — Medium — demo hosting omits browser policy headers

The GitHub Pages root supplies HTTPS/HSTS but not the repository's CSP, frame protection,
content-type protection, referrer policy or permissions policy. The Vercel configuration
contains these headers, but it is not the live host. Impact is limited while the site remains
an unauthenticated local demo; production account functionality should not be enabled on this
host. **Required action:** deploy the production build through the configured Vercel/Firebase
path and verify the headers on the final domain.

### SEC-02 — Resolved — transitive Functions dependency advisories

The audit initially found three moderate advisories in `uuid` and `qs`. Firebase Admin and
Functions were upgraded, the runtime was moved to supported Node 22, and safe transitive
versions were pinned. Both production dependency audits now report no known vulnerabilities.

### SEC-03 — Informational — secret handling for future Gemini integration

The live client contains no Gemini key and the AI provider is disabled/fake. If enabled, the
key must be a server-side Firebase secret; it must never use a `VITE_` variable or be committed.
A consumer Gemini subscription is not itself an API key or a production quota agreement.

## Remediation applied during this audit

- Generated real GitHub Pages entrypoints for static application routes so fresh deep links
  resolve through a page file instead of relying only on a 404 fallback.
- Included the built-in published demo lesson in those entrypoints; future server-published
  dynamic lesson ids still rely on the fallback until production hosting is used.
- Preserved the 404 fallback for unknown/dynamic paths.
- Increased primary controls and audited compact controls to a 48 px touch target; added
  pressed/current semantics to progress filters and lesson steps.
- Upgraded Firebase Admin/Functions, moved Functions to Node 22 and cleared known production
  dependency advisories.
- Added an automated contract test for Pages entrypoint generation.
- Replaced the stale project checkpoint with the current deployment and content truth.
